# Webman 测试、调试与验证边界

仅在需要新增或运行测试、复现故障、排查日志/异常/事务、确认配置生效或说明验证范围时读取。本文件帮助选择证据，不把任意检查说成生产验证，也不授权在生产或未知数据环境执行测试、迁移、队列消费或重启。

## 先发现现有测试与风险

按任务需要检查 `composer.json`/`composer.lock`、`phpunit.xml`/`phpunit.xml.dist`、`tests/`、Composer scripts、CI 配置、测试 bootstrap、`.env`/测试环境变量，以及项目已有的 HTTP、数据库、队列和进程测试命令。先确认测试会连接哪些数据库、Redis、文件目录、外部服务和端口。

- 优先运行项目已有且与改动最相关的测试入口；不要因为 Webman 手册示例使用 PHPUnit，就迁移现有 Pest、定制脚本或其它测试体系。
- 缺少测试框架时，`composer require --dev phpunit/phpunit` 会修改依赖与锁文件，须先获得用户同意；安装后按当前项目运行模型判断是否需要 restart。
- 生产、共享或数据库目标不明的环境，默认只做只读/无副作用检查。完整 PHPUnit、种子数据、迁移、真实队列消费、外部回调或会清理数据的测试，必须先确认环境和授权。
- 测试中的配置加载、容器缓存和静态状态也受常驻 worker 影响；不要让测试依赖执行顺序、上一个请求或本地机器残留数据。

## 按风险匹配证据

| 改动或问题 | 最小有价值验证 | 不能据此声称 |
|---|---|---|
| PHP 语法、类名、静态依赖 | 修改文件的 `php -l`、项目已有静态检查 | 自动加载、配置生效、HTTP 行为、数据库正确性。 |
| 纯函数或可隔离业务规则 | 有针对性的单元测试 | 路由、中间件、真实数据库/Redis、并发行为。 |
| 配置、异常/日志契约 | 受控 bootstrap 或项目测试 + 配置键/错误体断言 | 已在目标 worker、代理或生产环境生效。 |
| 路由、控制器、中间件、上传 | 隔离服务上的真实 HTTP 请求，同时断言成功和拒绝路径 | CDN/代理、TLS、真实用户权限或多进程容量。 |
| 数据库、事务、迁移、缓存 | 明确的测试连接、前后数据断言、回滚/失败路径 | 生产数据安全、锁竞争、跨库或高并发正确性。 |
| 队列、定时器、自定义进程 | 真实消费者/进程启动、成功与失败日志、可观察结果 | 重试、重复投递、集群唯一性或故障恢复。 |
| 协程、连接池、状态污染 | 目标驱动下的并发请求与资源释放验证 | 单请求、单 worker 或仅静态检查即可证明并发安全。 |
| Nginx/HTTPS/可信代理 | 从真实入口访问，并检查拒绝与 Header 边界 | 仅后端端口 `curl` 即可证明公网安全。 |

任务报告应列出实际执行的命令、环境、关键结果和未验证项；不把“命令成功退出”扩展为没有观察过的结论。

## 单元与集成测试

`webman` 的 PHPUnit 示例使用项目根目录 `phpunit.xml`、`support/bootstrap.php` 与 `tests/`；已安装 PHPUnit 时可从项目根目录使用当前项目约定的 runner，例如 `php vendor/bin/phpunit <目标测试>`。先查看 `--help`、测试 bootstrap 与配置，再选择单个目标或完整套件。

- 为新增行为测试正常、非法输入、权限拒绝、异常和边界条件；不要只覆盖 200 响应。
- 测试 Webman 控制器时，以真实 `Request`/HTTP 行为为准，不把手工构造数组当作路由、中间件或上传测试的替代品。
- 数据库测试使用专用可恢复数据库和明确连接名。若通过事务回滚隔离，先确认被测代码与测试使用同一连接；DDL、外部服务、队列消费者和其它进程通常不受该回滚保护。
- 给测试用的文件、缓存键、队列名和端口加唯一前缀并在受控范围清理；清理不能使用生产共享目录、全局 `Cache::clear()` 或无前缀队列。
- 网络、时间、随机数、邮件/支付/HTTP 客户端等外部依赖，优先沿用项目已有的 fake、mock 或本地替身。没有可验证的替身时，明确它是未执行的集成验证，不要发送真实副作用请求。

数据库、事务与缓存细节读取 [data-recipes.md](data-recipes.md)；HTTP 与上传读取 [http-recipes.md](http-recipes.md)；队列、定时器与自定义进程读取 [process-and-async.md](process-and-async.md)；协程验证读取 [coroutine-runtime.md](coroutine-runtime.md)。

## 调试与日志定位

先建立可重复的最小触发条件，并记录时间、请求/任务标识、路由、worker/进程、版本和相关配置变更。按时间顺序看入口日志、异常日志、队列/进程日志和依赖服务日志，先定位最早的因果错误，避免只修复后续的包装异常。

- Webman 的异常处理由 `config/exception.php` 决定。开发环境的 `app.debug=true` 会使异常响应包含更多细节；生产环境不要为了调试而向客户端打开堆栈或敏感配置。应通过受控日志和受限诊断收集信息。
- 使用项目现有 `support\Log` channel 和结构化 context 记录可关联字段，例如请求 ID、业务 ID、租户/用户的非敏感标识、路由和异常类型。不得记录密码、Token、Cookie、完整授权 Header、上传内容或原始敏感请求体。
- 不用 `echo`、`var_dump` 或 `exit` 调试 HTTP worker；它们会破坏响应或 worker 生命周期。临时诊断代码也应可移除、无密钥且不改变请求状态。
- 事务问题先核对 begin/commit/rollback 是否使用同一连接，并捕获 `\Throwable`。出现 `Uncommitted transactions` 日志时，沿该关键字、请求路由和连接名回溯；`webman/log` 是可选组件，安装它需要授权且需要 restart。

## 进程、文件监控与复现

Webman 的 monitor 进程可在开发中监听文件变化并自动 reload，也可监控内存并安全重启接近 `memory_limit` 的进程。它不是测试框架，自动 reload 或一次内存重启不能证明改动正确、内存泄漏已修复或多进程安全。

- 修改监控范围、进程或事件循环前读取 [core-runtime.md](core-runtime.md)；避免监控巨大的生成目录或依赖目录。Windows 需通过项目的 `windows.bat`/`php windows.php` 才能启用文件监控，内存监控不支持 Windows。
- 复现后台问题时，确认 worker 数、进程名、启动方式、队列消费者、监听端口、协程驱动和配置版本。单个 CLI 或单 worker 的复现不能代表集群。
- 排查偶发状态串扰时，至少用两个不同身份/参数交替请求同一 worker，并检查控制器属性、静态变量、单例、容器缓存和协程 Context；详见 [core-runtime.md](core-runtime.md)。

## 交付前的诚实结论

完成后按以下形式说明：

1. 已验证的行为及其环境，例如“隔离测试库中，指定测试通过”。
2. 运行过的检查，例如 PHP 语法、单元测试、真实 HTTP、消费者或进程状态。
3. 未运行的高风险验证及原因，例如“未连接生产数据库”“未启动真实消费者”“未进行并发/代理验证”。
4. 下一步需由用户或运维确认的外部操作，例如测试环境凭据、迁移窗口、重启或发布。

来源以目标项目的测试配置、锁定依赖和官方 PHPUnit/监控/事务/异常文档为准；本文件不替代 PHPUnit、Monolog、数据库驱动或压测工具的完整说明。
